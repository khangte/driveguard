# Claude 개발 지시문: 졸음 감지 측정값 수집

## 1. 요청과 목표

DrowsyDrive Android 앱에 **개발용 측정 로그 수집 기능을 구현**해 주세요. 계획 제시에서 끝내지 말고 코드 구현, 관련 검증, 사용 방법 안내까지 완료해 주세요.

현재 졸음 판단 기준을 개선하기 전에 실제 기기에서 출력되는 값과 판정 흐름을 확보하려는 작업입니다. **DB나 서버 없이 앱 내부에 세션별 JSONL 파일을 저장하고, Android Studio에서 PC로 가져와 분석하는 방식**으로 구현합니다.

JSONL은 한 줄에 JSON 객체 하나를 저장하는 UTF-8 텍스트 형식입니다. 관측값과 이벤트를 시간순으로 기록합니다.

### 완료 후 가능해야 하는 일

1. 디버그 앱에서 테스트 시나리오를 지정하고 수집을 시작·중지한다.
2. 눈·입·얼굴 자세 등의 측정값과 누락·초기화 사유를 확인한다.
3. 측정값 → 판정 결과 → 실제 알람 표시를 연결해 분석한다.
4. 저장된 파일을 PC로 가져온다.
5. 로그 수집이 꺼져 있거나 실패해도 기존 감지 기능은 동일하게 동작한다.

## 2. 작업 원칙과 범위

- 작업 전 저장소 지침과 최신 코드를 확인하고, 사용자가 이미 수정한 내용을 보존하세요.
- 기존 Java/Kotlin 혼용 구조와 Compose 화면 상태 관리 방식을 따르세요.
- 기존 졸음 감지 알고리즘과 알람 동작을 보존하세요. 이번 작업은 관측과 기록 기능 추가입니다.
- 필요한 최소한의 클래스와 변경으로 구현하세요. 전용 기록 클래스 하나를 중심으로 구성하되, 테스트를 위해 필요한 작은 데이터 구조는 허용합니다.
- Android/Java/Kotlin 표준 기능과 기존 의존성을 우선 사용하세요.
- Android Studio 도구를 사용할 수 있으면 IDE의 읽기·편집·검색·실행 도구를 사용하세요. 사용자의 미저장 변경을 덮어쓰지 마세요.

### 이번 작업에서 추가하지 않을 기능

- Room, SQLite 또는 외부 DB
- 서버, Firebase, 클라우드 업로드, 원격 분석 SDK
- 얼굴 사진·영상·음성 저장
- GPS, 블루투스 주소, 기기 고유 식별자 수집
- EAR, PERCLOS, 히스테리시스, 개인별 보정 등 새 졸음 판단 로직
- 분석 간격·눈 감김 기준·하품 기준·관측 공백 기준 변경
- 앱 내부 통계 대시보드, CSV 변환기, 공유·내보내기 화면
- 백그라운드 카메라 수집 또는 별도 서비스

### 보존할 현재 동작

작성 시점에는 다음 값과 정책을 사용합니다. 최신 코드가 달라졌다면 현재 값을 확인하고 보존하세요.

- 분석 시작 간격: 최소 250ms
- 눈 감김: 양쪽 눈 열림 확률 모두 0.2 미만, 1,000ms 이상
- 하품: 현재 입·코·오른쪽 눈의 Y좌표 비율 0.80 초과 및 웃음 확률 0.2 미만, 2,500ms 이상
- 연속 관측으로 인정하는 최대 간격: 1,000ms
- 같은 감김·하품 상태에서 판정 이벤트는 한 번 발생
- 누락·실패·대상 변경·세션 변경 시 기존 정책대로 초기화
- 이전 분석 세션의 늦은 결과는 현재 판정과 알람에 반영하지 않음

문서의 제안값인 0.35/0.65 등의 임계값을 이번 구현에 적용하지 마세요.

## 4. 저장 위치와 파일 정책

### 저장 위치

`context.noBackupFilesDir` 아래 `detection-logs` 디렉터리에 저장하세요.

```text
<noBackupFilesDir>/detection-logs/
  session_<시작시각>_<임의ID>_part001.jsonl
  session_<시작시각>_<임의ID>_part002.jsonl
```

- 실제 경로는 Android API로 구하고 하드코딩하지 마세요.
- 이 위치는 Android 자동 백업에서 제외됩니다.
- 앱 삭제·데이터 초기화로 로그가 사라질 수 있으므로 사용 안내에 명시하세요.
- 캐시 디렉터리나 공용 Downloads에 자동 저장하지 마세요.
- 저장소 접근 권한이나 네트워크 권한을 새로 추가하지 마세요.

### 초기 상한

- 파일당 약 10MiB에서 다음 파일로 분할합니다.
- 전체 로그는 100MiB를 상한으로 관리합니다.
- 오래된 닫힌 파일부터 삭제하고, 쓰는 중인 파일은 삭제하지 않습니다.
- 같은 세션의 이전 분할 파일도 닫힌 파일이면 정리 대상이 될 수 있습니다.
- 정리 실패로 상한을 지킬 수 없으면 수집을 오류 상태로 전환하고 감지는 계속합니다.
- 상한은 이름 있는 상수로 관리하고, 제한 처리를 테스트할 수 있게 하세요. 별도 설정 화면은 필요 없습니다.
- 각 분할 파일은 세션·분할 번호와 설정을 확인할 수 있는 헤더로 시작합니다.

## 5. 로그 형식과 필수 데이터

구체적인 필드 이름은 구현에 맞게 정하되 아래 의미를 보존하세요. 스키마 버전은 최초 `1`로 시작합니다.

### 5.1 공통 정보와 시간

- 기록 종류 `type`, 로그 형식 버전 `schema_version`
- 수집 세션 ID, 분할 번호, 기록 순번
- 세션 경과 시간: `SystemClock.elapsedRealtime()` 계열의 동일한 시간 기준 사용
- 관측 관련 이벤트를 연결하는 관측 ID
- 분석 세션과 수집 세션을 연결할 수 있는 식별 정보

벽시계 시각은 세션 시작 정보로 기록하고, 지속 시간·관측 간격 계산에는 사용하지 마세요. 현재 코드의 `frameTime`은 **촬영 시각이 아니라 분석 시작 시각**입니다. 파일에서도 의미를 구분하세요. 카메라 타임스탬프를 추가한다면 별도 필드로 보관하고 시계 기준을 확인하지 않은 채 서로 빼지 마세요.

여러 스레드에서 이벤트가 발생할 수 있으므로 발생 시각과 기록 순서를 구분할 수 있어야 합니다.

### 5.2 세션 시작 정보

- 앱 버전명·버전 코드와 알고리즘/설정 버전
- 제조사·기기 모델·Android API 수준
- 설정된 분석 간격과 실제 적용 중인 임계값
- 눈 감김·하품 지속 시간 기준과 허용 관측 공백
- ML Kit 감지 옵션
- 테스트 시나리오 이름
- 세션 시작 시각

기기 고유 ID나 사용자 이름을 기록하지 마세요. 설정값은 가능하면 실제 코드의 값을 참조해 기록하고 별도 복사본과 어긋나지 않게 하세요.

### 5.3 관측 기록

**분석한 결과 1회당 관측 기록 1개**를 저장합니다. 여러 얼굴은 그 기록 안의 배열로 표현하고 선택 대상을 표시합니다.

| 범주 | 필수 데이터 |
| --- | --- |
| 시간 | 분석 시작·완료 시각, 처리 시간, 이전 분석 시작과의 간격 |
| 입력 | 이미지 너비·높이, 회전 정보 |
| 얼굴 | 얼굴 수, 후보별 추적 ID, 얼굴 영역 좌표·크기 |
| 대상 | 선택된 후보, 대상 선택·변경 사유 |
| 눈 | 양쪽 눈 열림 확률 및 누락·무효 여부 |
| 입 | 웃음 확률, 현재 식에 사용하는 입 아래·코 아래·오른쪽 눈 좌표, 계산된 비율 |
| 자세 | 얼굴 Euler X/Y/Z 값 |
| 판정 | 선택 대상의 눈 감김·하품 조건 충족 여부, 각 타이머 상태·경과 시간, 이번 관측의 경고 발생 여부 |
| 유효성 | 실제 판정에 사용됐는지, 사용하지 않았다면 그 사유 |

- 실제 알고리즘에 쓰지 않는 얼굴 각도를 기록하더라도 이를 새 필터로 적용하지 마세요.
- 누락값은 `null`로 기록하고 사유를 남기세요. `0`으로 대체하지 마세요.
- NaN·Infinity는 JSON 숫자로 쓸 수 없으므로 `null`과 무효 사유로 변환하세요.
- 얼굴 미감지도 `face_count = 0`인 정상적인 관측 기록으로 남기세요.
- 분석 실패는 별도 실패 이벤트로 남겨 관측 공백과 구분하세요.
- 값이 유효하지 않으면 미계산 항목을 `null`로 두세요. 누적 시간 0과 미계산을 구분하세요.
- ML Kit 결과를 파일 쓰기 스레드로 직접 넘기지 말고 필요한 값만 복사하세요.
- CameraX 이미지 객체를 기록용으로 보관하거나 이미지 해제를 지연하지 마세요.

### 5.4 판정 초기화와 이벤트

다음 사유를 구분할 수 있게 기록하세요. 관측 기록의 사유 필드 또는 연결된 이벤트로 구현해도 됩니다.

- 감김·하품 조건 해제
- 필요한 값 누락·무효
- 얼굴 미감지
- 대상 변경
- 허용 관측 공백 초과
- 분석 실패
- 분석 세션 변경·화면 중단

기존의 경고 억제 상태와 타이머 동작을 바꾸지 않고 실제 내부 상태를 기록하세요. 진행 중이던 상태가 초기화된 경우와 처음부터 비활성인 경우도 가능하면 구분하세요.

알람은 **판정 이벤트 발생 / 알람 요청 / 중복 억제·대기 / 팝업 표시 / 사용자 중지**를 구분하세요. 기존 흐름에서 관측할 수 있는 지점을 기록하고, 요청 또는 팝업 표시를 실제 경고음 재생 완료라고 표현하지 마세요. 이를 위해 사운드·TTS 내부 동작을 대규모로 변경하지 마세요.

### 5.5 종료와 수집 상태

- 정상 종료 사유, 관측 수, 저장 수, 로그 유실 수, 파일 목록 등을 종료 기록에 남깁니다.
- 강제 종료 시 종료 기록이 없을 수 있습니다. 이런 파일을 완전한 세션으로 간주하지 않도록 안내합니다.
- 수집 시작·중지·실패는 Logcat에도 간단히 남깁니다. 매 관측의 전체 데이터를 Logcat에 중복 출력하지 않습니다.

## 6. 수집 제어와 생명주기

- 디버그 빌드에서만 간단한 수집 시작·중지 UI를 제공합니다.
- 시작 전에 시나리오 이름을 지정할 수 있게 합니다. 수집 중에는 변경하지 않거나 변경 시점을 명시적으로 기록합니다.
- 상태는 최소 `중지 / 수집 중 / 오류`를 구분해 표시합니다.
- 릴리스 빌드에서는 제어 UI가 없고 측정 파일·기록 스레드·직렬화 작업도 생성되지 않도록 합니다.
- 수집을 시작했다고 카메라나 권한 정책을 변경하지 않습니다. 카메라 권한이 없거나 분석이 비활성인 경우 시작 불가 사유를 안내합니다.
- 화면이 중단되면 현재 수집 세션을 닫습니다.
- 사용자의 수집 의도가 유지된 상태로 화면에 복귀하면 새 세션으로 시작합니다. 이전 세션의 타이머와 파일에 이어 붙이지 않습니다.
- 사용자가 명시적으로 중지하면 복귀해도 자동으로 다시 수집하지 않습니다. 앱 프로세스를 새로 시작하면 기본은 중지 상태입니다.
- 앱 종료·반복 시작·중지에서 파일 및 실행기가 누수되지 않게 합니다.
- 이전 분석 세션의 늦은 콜백은 새 세션 파일에 섞이지 않게 합니다.

## 7. 비동기 기록과 실패 처리

- 메인 스레드와 얼굴 분석 스레드에서 파일 열기·쓰기·정리·flush·close를 하지 마세요.
- 단일 기록 작업자와 크기가 제한된 대기열 등 단순한 구조로 구현하세요.
- 기록 요청은 필요한 값의 불변 스냅샷을 짧게 전달하고 돌아와야 합니다. JSON 직렬화도 가능하면 기록 작업자에서 수행하세요.
- 대기열이 가득 차면 분석을 기다리게 하지 말고 관측 로그를 버리되 유실 개수를 기록·표시하세요.
- 종료·닫기 요청은 대기열 포화로 사라지지 않아야 합니다.
- 정상 종료 시 이미 받아 둔 기록을 순서대로 처리한 뒤 닫으세요. 메인 스레드를 대기시키지 마세요.
- 약 1초 간격을 목표로 버퍼를 flush하고 정상 종료 때 남은 버퍼를 처리하세요. 매 관측마다 디스크 동기화를 강제하지 마세요.
- flush를 했다고 전원 차단까지 포함한 영구 저장을 보장한다고 표현하지 마세요.
- 저장 공간 부족·I/O 오류 시 수집 오류를 알리고 안전하게 정리하되 기존 감지·알람을 중단하지 마세요.
- 프로세스 강제 종료로 마지막 줄이 잘릴 수 있습니다. 파일 형식과 분석 안내에서 끝의 불완전한 줄을 구분하도록 하세요.

순수 Java 판정 클래스에 Android Context, 파일 I/O, JSON 의존성을 넣지 마세요. 진단 정보 전달이 필요하면 기존 로직과 같은 계산 결과를 이용하는 작은 데이터 구조로 확장하세요. 별도 로깅용 판정기를 돌려 결과를 재계산하지 마세요.

## 8. 테스트 시나리오와 정답 표시

측정값 자체는 모델 출력이며 실제 졸음의 정답이 아닙니다. 정차 상태에서 다음 시나리오를 구분해 수집할 수 있게 하세요.

| 시나리오 예시 | 목적 |
| --- | --- |
| 정면 눈 뜸·일반 깜빡임 | 평상시 값과 흔들림 |
| 눈 감김 0.5초·1초·2초 | 감김 시간과 경고 지연 |
| 좌우 보기·고개 숙임 | 얼굴 방향과 분류값 변화 |
| 말하기·웃기·하품 | 현재 하품 지표의 반응 |
| 얼굴 가리기·다중 얼굴 | 누락 처리와 대상 선택 |

세션 시나리오 이름만으로 매 순간의 실제 행동이 확정됐다고 취급하지 마세요. 정차 실험에서 관찰자가 사용할 수 있는 간단한 행동 시작·종료 마커를 제공하고, 세션 경과 시간과 연결해 저장하세요. 정교한 라벨링 도구나 영상 저장은 필요 없습니다. 마커도 사람의 반응 지연이 있는 참고 기록임을 안내하세요.

## 9. 검증 요구사항

변경과 직접 관련된 검증을 수행하고, 실행한 결과와 미실행 항목을 구분해 보고하세요.

1. **기존 동작 보존:** 감지·운전자 선택·알람 관련 기존 테스트를 실행합니다. 동일한 관측 시퀀스에서 수집 활성/비활성에 따른 경고 시점·횟수가 동일한지 대표 사례를 검증합니다.
2. **파일 형식:** 모든 완전한 줄이 JSON으로 읽히며, 누락값·비유한 값·얼굴 미감지가 올바르게 표현되는지 검증합니다.
3. **보관과 실패:** 작은 테스트 상한으로 파일 분할·오래된 파일 정리·저장 실패·대기열 포화와 유실 집계를 검증합니다.
4. **생명주기:** 반복 시작·중지, 화면 중단·복귀, 이전 세션의 늦은 결과에서 파일 혼입과 자원 누수가 없는지 확인합니다.
5. **빌드와 UI:** 관련 단위 테스트, debug 빌드, 관련 lint를 수행합니다. 릴리스에서 수집 진입과 파일 생성이 차단되는지도 확인합니다.
6. **실기기 확인:** 가능한 경우 짧은 수집을 수행해 실제 파일을 PC로 가져오고 값·세션 정보·상태 표시를 확인합니다. 기기가 없으면 이 항목은 미실행으로 보고합니다.

현재 구조에 맞는 기존 테스트 도구를 사용하세요. 테스트만을 위한 무거운 프레임워크나 큰 추상화는 추가하지 마세요.

실기기 측정 전에는 로그 추가의 처리 시간·배터리 영향이 없다고 단정하지 마세요. 수집 활성/비활성의 실제 분석 간격과 처리 지연을 비교할 수 있게 하세요.
